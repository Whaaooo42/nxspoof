How it's built

For working on NXSPOOF: how the code is organized, the rules that keep it organized, and where new features go. The why of each choice is in Decisions; the parts at run time are in How it works. Standard-library Python 3.9 (Apple's own), nothing to install.

Principles · Layers · The design · Safeguards · Modules · Platform contract · Adding a feature · What's next

Principles

  • Black boxesEach module has one job, owns its state, and is used only through a small interface.
  • No globalsObjects are created once in app/ and handed to whoever needs them.
  • Imports go downThe layers below; a test enforces it, which also rules out circular imports.
  • One event busEverything said or that happens is one event: a technical text, an optional casual one, a level, a fact.
  • Only macos/ talks to the MacCommands, pf, sharing, ownership. It never logs: it returns values or raises.
  • One ordered shutdownFor every way a run can end; each step protected on its own.
  • Standard library onlyApple's python3 3.9, no 3.10+ syntax.
  • A hobby projectNo plugin systems, asyncio, class hierarchies, frameworks or build steps.

Layers

The design

Events and logs

bus.log(tag, technical, casual=…, level=…, fact=…), bus.say(casual), bus.fact(kind). Sinks (the Terminal, the log file, the records, the dashboard) run in order under one lock; listeners (the story, the services) after it. A line that matters to listeners carries its fact: one event, so the line always comes before what listeners do. Every event lands in the run's records, logs/<run>.jsonl: programs read those, never the text (only features/textlog.py knows the text, for runs before 2026-11-15).

Marked, never searched for

Console names come from the registry as Marked text, and lines are built with compose("…%s…", registry.name(mac)) (core/text.py), which keeps the marks; outcome words with outcome("BLOCKED", "blocked"). The Terminal and the dashboard color exactly those stretches; searching a line would also catch a model or an old name. A name used as plain text on purpose: str(...).

Settings

settings/schema.py describes every field once: default, type, help, now or next start. Configure, validation, the SETTINGS lines and the reference table all come from it. settings/store.py saves as a tidy rewrite, through a checked temporary file. The store is quiet: whoever changes a setting announces it. app/config.py merges settings and options into one RunConfig.

A run's life

app/start.py: the program copy, the checks, the lock, the background, then keeper.split() before any thread exists. app/run.py: sharing on, wait for the hotspot, DNS, firewall, web, monitors, self-test, READY, the one answer. Stop requests (a note, a signal) set one flag. The ordered shutdown: servers, firewall counters and rules, summaries, sharing off, cable out, Stopped.; each step only if its resource was taken, and one failure never skips the rest.

The run writes, the others read (D30)

The run holds run.lock and writes run.json (where it is), run_state.json (what the page shows, every second while it changes) and its records; it reads settings.json again when it changes (features/settingswatch.py) and takes a Stop's note from stop.json. The dashboard (app/runfollow.py) finds it by the lock and follows those files. A run never serves a page.

Minimal root (D24)

macos/privsep.py starts the run as a brand-new process (D33): the original stays root as the keeper; the run is launched with your groups, gid and uid already set, in that order, so it can never come back (it checks first thing). One length-prefixed JSON message at a time over a socket pair, file descriptors alongside. The run's KeeperSystem turns root calls into requests; the keeper checks each against CHECKS, builds the firewall rules itself, and opens the servers' sockets. A new root need is a new checked request, with its test in tests/test_keeper.py.

Files have one owner

settings.json: settings/store.py; logs and records: output/logfile.py; the run's files: output/runfile.py; the data folder and the program copy: output/datafolder.py. Everything created is handed back to you (macos.user.give_to_user). Where files go is asked of core/places.py, by role.

Where macOS keeps the hotspot

Name, channel, security: /Library/Preferences/SystemConfiguration/com.apple.airport.preferences.plist, section InternetSharing (the SSID as bytes), readable without root. The password: the System keychain (account AirPort). com.apple.nat.plist's AirPort section is stale: never read the name there. Name and password go together: writing one alone breaks the hotspot (Run H), so NXSPOOF only reads.

Safeguards

Three layers, all automatic on every test run (python3 -B tools/run_tests.py, on Apple's 3.9 and a newer Python), so new code keeps to the principles and nothing gets mangled quietly.

1 · Guardrails: hard rules (tools/guardrails.py)

Each rule is a function given a project folder that returns the places breaking it, with what to do; the tests fail on any. Exceptions sit in its ALLOWED_* tables, each with its reason: a new one is a visible decision, never an accident. It measures every file of nxspoof/ and tools/, every function, and blocks of 8+ lines that appear twice, against the last accepted state (tools/health_baseline.json). Slow creep counts too: a file growing by 30 % (and 60+ lines) or a function's complexity by 40 % (and 4+). from the code

3 · The memo (MEMO.md)

After every test run the watchdog writes it when something new needs a look (what, where, what to do), and removes it when there's nothing to say. Fine as it is: python3 -B tools/health.py --accept "why", kept with its reason in the baseline's history. Proof that they bite: tests/test_guardrails_bite.py copies the project, plants one violation per rule (a print() in a feature, an inline script, a 130-line function, a stale generated table…) and checks the right safeguard names it. A new rule always comes with its proof.

The safeguards are the owner's: never loosen a rule, raise a limit or add an exception without the owner's OK (CLAUDE.md).

Validation

  1. Unit tests: every module, with faked command outputs and real samples (tests/fixtures/); exact answers that must never drift (colors, DNS replies byte for byte, the sharing settings written, Wi-Fi tracking, settings defaults) are pinned in tests/fixtures/golden.json. tests/__init__.py swaps the data folder for a temporary one.
  2. The guardrails and the watchdog, at the end of the tests.
  3. The simulated session (tools/simulate.py new --out <tmp>, then --compare tests/fixtures/reference/run <tmp>): the real start-to-stop run on a fake Mac, fake consoles joining, passing, getting blocked, FTP, leaving and coming back. The technical log, the casual transcript and the dashboard snapshots must match the reference run of today's code (--stop dashboard: run_dashboard_stop; --keeper: through a real keeper). An intended change: record the reference again, and say what changed.
  4. Real runs with the Switches (Real runs), each checked from its records.

Code conventions

  • A one-line # comment directly above every function, class and method (JS: //); no docstrings except the file header, whose first line is name - its job (the modules table is made from it).
  • Never two empty lines in a row. Section banners exactly 160 wide, with an empty line above and below.
  • A thorough technical log; a casual line wherever it means something to a person; problems always show.
  • A new option gets a --flag and its help; a new command, a menu row; a new file, its row in the reference.

What's next

The foundation is complete; D30 untangled the parts. Next: Run I on the real Mac, then the public release. Then what each console reaches beyond the test (its FTP app, any other port), and the bigger plans below, designed but not built.

Allowlist mode refuses to start without a working uplink: it never quietly falls back to full internet. Every allowed connection is logged and counted, like blocked ones.

Who may reach what: the rule order (D12, D13) · planned

net/policy.py answers one question for everyone (DNS, firewall, dashboard, logs): may this console reach this name? The first rule that matches wins:

  1. The connection test names: answered by the Mac (it's what NXSPOOF is for).
  2. The blocklist, global (lists/blocklist.txt: one name or *.pattern per line, sources noted): blocked for every console, never a request, no allow button; only the file changes it.
  3. Allow once (this console, this run).
  4. This console's denylist, then its allowlist.
  5. The global denylist, then the global allowlist.
  6. Everything else: blocked, and becomes a request.

The blocklist beats everything; a console's own rules beat global ones; deny beats allow at the same level. So *.nintendo.net on the blocklist blocks all of Nintendo except the two tests, and no allowlist can override it.

The Requests inbox (D11) · planned

Every attempt blocked by "everything else" becomes a request, grouped by console and name, with a count and a suggested wider rule (*.github.com for api.github.com). One click: allow once, allow for this console, allow for all, mute for this console, mute for all (saved in settings.json). Decisions apply live: consoles retry blocked lookups constantly, so an allowed name usually works within seconds. Optional "ask first": hold a never-seen name a few seconds while the dashboard asks. History kept in logs/requests.json. In sealed mode decisions are saved for the next allowlist run. Later: firewall drops of direct-to-address attempts (pf's log) as requests too. Same safety as every control: no allowing *, a bare top-level domain, or anything the blocklist covers; every decision logged.

Services per console · planned

Each console lists its services (name, port, kind of check); features/services.py runs one watcher per service with today's FTP timing, each emitting service.up / service.down, so the logs, the story, the dashboard and the summary handle a new service with no extra code. Controls attach to services (Open in FileZilla on FTP).
