The connection test, packet by packet

What happens, technically, from the moment a Switch asks for its connection-test name to the moment it says "connected", with the files that do each step. The friendly overview is How it works.

0 · An address, and a name for the console

  • The Switch joins the hotspot. macOS's own DHCP server (bootpd) gives it an address, say 192.168.2.3, with 192.168.2.1 (the Mac, on bridge100) as its router and its DNS server.
  • pf lets that exchange through: pass in quick on bridge100 inet proto udp from any port 68 to any port 67.
  • NXSPOOF reads macOS's lease file (/var/db/dhcpd_leases, macos/leases.py) and learns this address is that MAC address, which settings.json names "Switch 2". From now on everything from 192.168.2.3 is Switch 2's (consoles/tracker.py, on_dhcp): DHCP gave address 192.168.2.3 to Switch 2 (…), fact console.address.

1 · The DNS question

  • One UDP packet to 192.168.2.1:53: type A (an IPv4 address) for ctest.p01.ctest.srv.nintendo.net? (a Switch 1 asks for ctest.cdn.nintendo.net). It often asks for AAAA (IPv6) too.
  • pf, on the way in, in order: IPv6 is dropped first (block drop in quick on bridge100 inet6 all); this packet matches pass in quick on bridge100 inet proto udp from any to 192.168.2.1 port 53.
  • Plan B: when macOS already holds port 53, NXSPOOF listens on 5354 and a redirect moves the packet there (rdr pass on bridge100 inet proto udp from any to 192.168.2.1 port 53 -> 192.168.2.1 port 5354). The Switch never knows.
  • The socket was opened by the keeper (only root may open ports below 1024 on one address) and handed to the run, which isn't root, over a private channel (file-descriptor passing, app/keeper.py). The code that parses what the Switch sent never runs as root.

2 · The DNS server answers

net/dns.py, build_reply, pure functions tested with real packets:

  1. Header: 12 bytes: transaction ID, flags, number of questions. A packet that is itself a response, has no question, or is shorter than 12 bytes is ignored.
  2. Name: length-prefixed labels (5ctest 3p01 5ctest 3srv 8nintendo 3net 0). A compression pointer inside a question is refused as junk.
  3. Type and class, 2 bytes each.
  4. Decision (net/policy.py), on the name lowercased, trailing dot removed. Only an A or ANY question gets an address: a test name → 192.168.2.1; anything else → 0.0.0.0 ("nowhere"); AAAA and other types → an empty "no error" reply: as far as the Switch can tell, there's no IPv6 here.

Sent straight back, in well under a millisecond. Then it's written down: consoles/tracker.py, on_dns, finds which console has that address, updates its counters, and logs, with the console's name marked (so the Terminal and the dashboard color exactly that):

DNS   Switch 2 (192.168.2.3) asked A     ctest.p01.ctest.srv.nintendo.net -> 192.168.2.1  (Switch 2 connection test)

A blocked name says -> BLOCKED instead and carries the console.blocked fact with the running total: the card's "N attempts blocked".

3 · The test page

  • A TCP connection to 192.168.2.1:80; pf lets it in (pass in quick on bridge100 inet proto tcp from any to 192.168.2.1 port 80) and keeps its state, so the replies flow back.
  • GET / with Host: ctest.p01.ctest.srv.nintendo.net, and the Switch's network stack in the User-Agent: libcurl (nnNifm; …) for a Switch 2, NX NIFM/00 for a Switch 1.
  • net/web.py decides from the Host header, through the same policy as DNS:
HostAnswer
a test name200 OK, Content-Type: text/plain, Content-Length: 2, X-Organization: Nintendo, Cache-Control: max-age=0, no-cache, no-store, Pragma: no-cache, body ok (exactly Nintendo's, checked live 2026-11-13)
anything else403, empty, connection closed

4 · "Online", and right after

consoles/tracker.py, on_http: the first test passed during this visit raises console.online. The card turns online, the casual log says Switch 2 thinks it's online, all good, and the technical log:

HTTP  Switch 2 GET http://ctest.p01.ctest.srv.nintendo.net/  (UA: libcurl (nnNifm; …)) -> 200 ok  (Switch 2 connection test)
  • The Switch's network manager (NIFM) sees what it expects (status 200, that header, that body) and shows "connected".
  • Then it tries its real servers (sign-in, update checks, game servers…). Each name gets 0.0.0.0: the connection fails on the console itself, and each attempt is logged and counted.
  • Anything aimed at an address it already knows is dropped by the last rule, block drop in quick on bridge100 all. pf counts those packets: the summary's "everything else (blocked)".
  • The 60-second lifetime means the Switch asks again now and then, and gets the same answer.
  • NXSPOOF's own self-test (before READY) sends the same requests with a marker header, so they're never counted as a console's.

See it yourself

  • The technical log (the dashboard's Technical, or the run's data/logs/<date>_<time>.log): the DHCP, DNS and HTTP lines above, for each console.
  • The self-test at every start: CHECK DNS PASS ctest.cdn.nintendo.net -> 192.168.2.1, CHECK HTTP PASS … -> 200 ok, and example.com -> 0.0.0.0 / -> 403 for the "everything else" side.
  • Without a Switch: python3 -B nx_spoof.py check (menu 8 → 3) runs the same servers on 127.0.0.1 with free ports, no admin rights.
