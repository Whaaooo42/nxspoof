How it works

A ten-minute read, without code: the trick, the three walls, and the four parts of NXSPOOF that make it all go. The packet-by-packet close-up is The connection test.

The trick

When a Switch joins a Wi-Fi network, it asks one question before calling itself online: "can I reach Nintendo's test page?" It looks up a test name (ctest.cdn.nintendo.net for a Switch 1, ctest.p01.ctest.srv.nintendo.net for a Switch 2), fetches a page from it, and checks the answer. NXSPOOF makes your Mac the Wi-Fi network, the name lookup and the test page, all at once: the Switch asks its question, gets exactly the answer it expects, and is happy. Every other question gets a polite "no".

The three walls

wall 1

No road out

macOS's own Internet Sharing makes the hotspot and hands out addresses. It insists on sharing from something: NXSPOOF gives it Thunderbolt Bridge with a fixed private address, a port with nothing behind it. A virtual cable (two virtual interfaces, gone at every restart, plugged back at every start) makes macOS believe it's connected.

wall 2

Names lead nowhere

Every device that joins asks the Mac for names. NXSPOOF's small DNS server answers the two test names with the Mac's address, and everything else (Nintendo's other servers, game and update servers…) with 0.0.0.0: BLOCKED. If macOS already holds the DNS port, NXSPOOF answers on 5354 and the firewall quietly redirects there ("plan B").

wall 3

A firewall that doesn't trust names

A program can skip the lookup and use an address it already knows. So NXSPOOF loads rules into macOS's firewall (pf), for the hotspot only: getting an address, asking a name, the test page; every other packet is dropped. pf counts the drops (the summary's "everything else (blocked)"). At Stop, NXSPOOF takes out its own rules, and only those.

the answer

The test page

The Switch fetches its test page from the Mac. NXSPOOF answers it exactly as Nintendo's server would (200 OK, X-Organization: Nintendo, ok; the log says 200 ok). That answer flips the Switch to "connected".

The hotspot's name, channel and password stay macOS's: you set them once in System Settings, and NXSPOOF only reads them (to show the name and check there's a password). Writing them behind macOS's back breaks the password: tried, and dropped (D25).

Watching: who's there, and what they try

  • Joining and leaving the Wi-Fi: macOS writes it in its kernel log, and NXSPOOF reads it live (a console that leaves shows up about 6 seconds later, 16 at most).
  • Which address each console got: from macOS's DHCP lease file.
  • What each console asks for: every DNS question and web request, matched to the console by its address.
  • Its FTP server (optional): NXSPOOF knocks on the console's FTP port now and then, to say when an FTP app on it is up.
  • The hotspot itself: every 5 seconds. If macOS drops it, NXSPOOF plugs the cable back in and turns sharing on again, and keeps trying until it's back or you Stop.

Consoles are recognized by their MAC address (the ones in settings.json); an unknown one shows up with Add this console.

The four parts

  • Only a Stop stops NXSPOOFClosing a window, a tab or the Terminal never stops a run. A run is always in the background. (A sleep ends it too: closing the lid is a way to say you're done.)
  • The run talks to nobodyIt writes files (its records, where it is, what to show) and reads settings.json. No web server of its own.
  • The dashboard finds the runNot the other way around. Open it whenever: it reads the run's records from the first line.
  • One way to startBoth doors run the same nx_spoof.py start, from the program copy, and get the run's one answer.
  • One run at a time, by a lockThe run holds a lock file. A free lock means no run, however the last one ended.
  • Minimal rootOnly the keeper is root, with a short checked list of jobs. The code that reads what consoles send runs as you.
process · runs as you

The run

Does the job, tells it in files.

  • DNS, the "ok" test page, the self-test
  • Watches consoles, FTP, and its hotspot
  • Holds run.lock; writes run.json, run_state.json and its records
  • Reads settings.json again when it changes
  • Stops on a Stop's note or a signal: firewall out, summary, sharing off, cable out
process · root

The keeper

The run's root part (D24).

  • Only its checked list, on request: Internet Sharing, NXSPOOF's firewall rules, the cable, ports 53 and 80
  • Cleans up if the run dies or freezes (no heartbeat for 30 s)
  • Ends with the run
process · runs as you

The dashboard

The page's server. Comes and goes with the page.

  • 127.0.0.1 only, the same port each time (remembered in dash.json)
  • Finds the run by its lock, shows it from its files
  • Writes settings.json (Configure, consoles)
  • This Mac, ▶ Start, ■ Stop (a note and a signal)
  • Leaves a few seconds after its last page closes
viewers

The page, follow

Show and ask, nothing else.

  • The page talks only to the dashboard; its buttons need the page's secret token
  • nx_spoof.py follow (menu 3, 4): the newest run's records, live, in the Terminal; Ctrl+C only stops watching

Where the words come from

Everything NXSPOOF says goes through one message bus. Each message has a technical text, an optional casual one (plain words with emoji) and a level; problems always show. The Terminal, the log file, the dashboard and the records are all listeners: the log file (data/logs/<date>_<time>.log) is the full technical story, and next to it the records (.jsonl) hold the same events as data, which programs read instead of picking through text (the dashboard, menu 6 → 1's checklist).

After a crash—the keeper; if even that couldn't happen, 🧹 Clean up

It doesn't touch the consoles (no modding, nothing installed on them), give them internet (by design, nothing gets through but the test), or change the hotspot's name, channel or password. Any device can join the hotspot, but only a Switch gets the test answer: everything else is refused, for every device.
